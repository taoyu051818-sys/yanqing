# 管理中心重构执行计划

## 目标

以“统一用户主档、领域状态机、账本事件、角色工作台、审批审计、端到端验收”为主线，完成延庆金羽场馆、会员、培训、球局/赛事、商品、联盟和财务的可运营闭环。模拟数据只用于演示，正式验收必须走 API 和持久化数据。

当前执行状态（2026-09-01）：阶段 0、1、2A、2B 和 2C 已收口；阶段 3 本地全新 PostgreSQL 已通过 29/29 个迁移、迁移状态和 Schema diff，本轮代码门禁为 shared 13/13、API 单元/服务 558/558、小程序 106/106、健康接口 E2E 1/1，且种子化验收库完成真实 HTTP/数据库闭环。生产环境仍须备份并重新取得目标库迁移证据。阶段 4 的测试号仅可预览、不支持上传，当前未上传且未代替用户真机验收。正式体验版、HTTPS 远端联调和用户真机验收需由部署方提供有上传权限的 AppID 与生产凭据。

## 时序与并行关系

```text
阶段 0 需求/现状冻结
        |
        v
阶段 1 领域模型与不变量（唯一门禁）
        |
        +--> 2A 管理中心工作台/导航/任务中心
        +--> 2B API 状态动作/账本/结算/权限
        +--> 2C 自动化测试/种子数据/验收脚本
        |
        v
阶段 3 联调与逆向流程回放
        |
        v
阶段 4 微信构建、测试 AppID、真机验收与交付
```

阶段 2A、2B、2C 只能在阶段 1 的对象名、状态名、动作前置条件和账本口径冻结后并行；任何一条工作流发现模型缺口，都先提交模型变更，再修改自己的实现，禁止各自定义同名状态。

## 阶段 0：冻结（已完成）

- 固化需求书的五条硬规则、会员端与前台/教练/主理人/赛事/商户/财务/管理员等运营角色，以及验收闭环。
- 盘点当前小程序、Web 运营台、API、Prisma 和 shared 领域规则。
- 识别当前缺口：角色页孤立、审批/待办不足、逆向冲正不完整、培训教务对象不足、联盟周期结算不足、库存盘点与日结不足。

## 阶段 1：领域基础（已完成）

### 必须先完成

- 统一对象：User/Family/Student、Lead、Membership、Order/Payment/Refund、Booking、TrainingContract/Session/Attendance/Consume、Game/Host/Registration、Event/Team/Match/Score、Merchant/Campaign/Coupon/Redemption/Attribution、SKU/StockTxn、Settlement、ApprovalTask、RiskCase、AuditLog。
- 每个对象明确状态机、允许动作、责任角色、可逆动作和审计字段。
- 订单拆分 paymentStatus、fulfillmentStatus、settlementStatus，不用一个 status 混合三种含义。
- 五账户独立账本；充值为预收，培训按消课确认收入；培训有效收入 20%形成场馆合同流水，培训占场不形成应付场租。
- 所有价格、规则、奖励、让分、退费政策采用生效时间版本，并把快照写入业务单据。
- 所有支付、退款、调账、库存、核销和结算动作支持幂等键；已入账记录不可物理删除，只能冲正或调整。
- 权限采用“动作 + 数据范围 + 金额阈值 + 场馆范围”，实现制单人与审批人分离。

### 阶段门禁

- 领域单元测试通过。
- 状态转移表、权限矩阵和账本不变量评审通过。
- 所有模块引用同一套枚举和规则，不得在页面中自定义状态。

## 阶段 2A：管理中心（本轮完成）

负责人：前端/交互工作流。

- 建立单一经营工作台：我的工作承接统一待办、岗位入口和经营分析；业务中心统一为今日营业、场馆资源、客户与会员、培训、球局、赛事、联盟、商品与库存、财务结算、治理与权限。
- 每个领域提供角色可见的列表、核心状态动作、异常队列、导出和审计；复杂工作台继续按对象拆出稳定详情深链，禁止为了增加菜单而复制业务规则。
- 角色工作台只显示当前岗位的待办和允许动作，不复制业务数据和业务规则。
- 增加业务中心搜索、待办收件箱、超时提醒和班次上下文；当前单馆范围只展示场馆与营业日，多场馆/跨营业日切换须在后端 scope 契约具备后再开放，禁止制作无效控件。
- 测试身份切换保留在测试配置下；生产身份模拟必须有独立审计和财务动作禁用。

## 阶段 2B：后端闭环（本轮完成）

负责人：API/数据库/领域服务。

- 补齐状态动作接口：提交、审核、退回、签到、消课、核销、纠错、退款、冲正、结算、关账，而不是直接更新状态。
- 实现工作流任务、审批阈值、maker/checker、风险队列和审计事件。
- 打通收入确认、预收负债、五账户、培训 20%合同流水、联盟结算、主理人奖励、库存成本。
- 实现并发锁场、支付回调幂等、库存原子扣减、券码一次性核销和重复请求防护。
- API 数据范围隔离：商户仅本商户，教练仅本班，前台不可调账，赛事岗位不可改财务。
- 完成会员产品、充值计划和场馆价格规则的有效期版本/启停；业务订单保存经济规则快照。
- 完成寄售订单版本 1 快照、履约应付、整单退款反冲和双人周期结算；周期结算可在源营业日锁定后继续流转。
- 完成强制退款不可驳回、`REFUND_PENDING` 履约/消课冻结，以及充值退款余额短款风险留痕。

## 阶段 2C：测试与数据（已完成，持续回归）

负责人：质量/产品验收。

- 为每条状态机编写正常、取消、退款、重试、越权、重复、弱网和人工修正用例。
- 准备覆盖会员、监护人、教练、前台、主理人、赛事、商户、库管、财务、老板的种子数据。
- 固化 18 条端到端验收旅程：获客推荐、订场、五账户/充值计划、培训消课、试听/监管、主理人、瑞士赛、联盟券、库存、寄售应付/结算、退款互锁/短款风险、日结、周期结算、权限、商业主数据、参数生效、导出审计和旧库 cutover。
- 自动检查所有关键单据是否能从用户、来源、订单、履约、账本、结算和操作者相互追溯。

## 阶段 3：联调门禁（实现完成，冻结验收中）

- 当前重点门禁：球局满员 FIFO 候补与退款递补、培训教练提案—管理员确认、赛事发布/五轮/完赛积分幂等、联盟券/结算状态、库存并发幂等、财务日结 REVIEW/LOCKED。
- 先打通一条最短闭环：推荐新客 → 订场 → 支付 → 签到 → 完成 → 收入确认 → 日结 → 看板。
- 再打通培训和联盟两条复杂闭环，验证预收、20%、券归因和商户独立收款。
- 最后接赛事、库存和跨模块退款，回放所有反向动作。
- 联调期间禁止新增菜单；新增需求必须先补对象、状态、权限和验收用例。

当前代码门禁为 shared 13/13、API 558/558、小程序 106/106、健康接口 E2E 1/1，本地数据库基线为 29/29 个迁移且 Schema diff 为空。已完成推荐绑定/首充/双边奖励、候补递补、赛事取消/退款、真实搭档授权、完赛封账、培训试听/监管/消课/冲正/结算、联盟结算、库存主数据与作业、寄售应付/反冲/结算、前台班次、现金差异、封场维护、履约确认和日结锁定等回放；旧 17 迁移环境上线前还须按 cutover 指南演练升级并保存证据。

## 完成定义

只有同时满足以下条件，阶段 3/4 才能关闭：

1. 正常路径和逆向路径都有持久化记录。
2. 每次跨角色交接都有下一责任人、SLA 和审计证据。
3. 金额、积分、库存和奖励均可冲正，不允许无痕覆盖。
4. 角色越权、商户越界、重复回调和重复核销均有自动拦截。
5. 自动测试、API 构建、小程序微信构建和真机验收全部通过。
