# 场地与营业时段工程收尾（2026-09-19）

本轮针对上次健康检查确认的四处技术债完成修改，仅本地开发和隔离验收，未提交发布或部署生产。

## 1. 统一历史经营口径

经营报表和老板摘要都按查询时段读取场地、营业时段的有效期，不再把当前启用时段套用到过去。老板摘要读取覆盖当天和前7日的同一事务快照，用于摘要与连续空场检测。

`capacity-courts.ts` 只读取场地有效区间，`capacity-slots.ts` 只读取营业时段有效区间；`venue-capacity.ts` 是共用的纯计算函数。按时间边界拆分计算，同一片场地的同一分钟只计一次，避免旧的两小时时段改为小时段、或者遗留重复时段后重复计数。预约与封场先按场地分组。

已确认预约即使处在场地停用、删除或调整营业时间之后，仍保留实占时长；不会因此虚增空闲容量。管理员补录到尚无营业配置记录的日期，实际预约归入“未配置时段”，只保留已知实占，不推测未知空场容量。没有数据的兜底时段不输出。

## 2. 独立业务历史与一次性旧数据迁移

增加 `CourtAvailability`、`TimeSlotAvailability` 两张有类型的业务历史表：有效起止时间、启用状态，时段历史还保存标签、起止分钟与时段分类。具有外键、起止约束、每个资源唯一当前版本，以及有效期索引。

历史由迁移中明确声明的数据库触发器维护。选择触发器，是为了让所有写入来源（API、种子脚本和直接SQL维护）都与业务历史同事务提交或回滚，避免某个调用者忘记追加历史。资源行锁串行化同一资源的状态变更，历史边界单调递增；普通名称修改不增加场地启停记录，未改变状态的更新不制造新版本。**业务代码不应直接修改历史表，后续修改历史规则必须以迁移和回归测试一起交付。**

仅在 `20260919010000_availability_history` 迁移中读取旧审计与已保存的营业配置，回填可恢复的历史。日常报表不再解析审计JSON，也不再加载全部审计事件。旧记录中没有证据的部分保留为 `BASELINE`，可恢复的迁移记录标记 `IMPORTED`，新变更为 `RECORDED`；不能把从未保存过的旧数据当作已精确还原。

球馆设置保存只更新实际变化的时段。单纯修改名称、地址、联系方式，不再先停用所有时段然后逐个启用，避免制造虚假的营业间断。

## 3. 明确的错误合同

共享包增加 `COURT_REVISION_CONFLICT`。后端异常响应、HTTP客户端、mock和页面使用同一业务码；显示文案可独立修改。兼容原有数字HTTP code和message，新增可选businessCode；500错误不会透传内部业务码。

小程序ApiEnvelope直接复用共享定义。冲突状态在重新加载失败后仍保留，避免网络报错覆盖中文文案后重新出现保存按钮。

## 4. 明确的异步结果与页面所有权

新增页面范围内的 `useSettingsMutation`，统一保存、删除的忙碌状态、账号/权限/页面生命周期、写入错误和后续刷新。

结果显式区分 `saved`、`saved-refresh-failed`、`failed`、`inactive`、`busy`，加载也返回明确状态。写入成功就清除可重复提交的旧草稿和详情；刷新失败显示“操作已保存，但页面刷新失败”，提供重新加载，不误报写入失败，也不允许直接重复提交。刷新期间持续保持忙碌状态。页面导航只接受明确的成功结果，旧账号或已销毁页面的回调不能操作当前页面。

这是当前页面三个变更操作共用的有限抽象，没有增加全局状态机框架。表单映射也已去重。

- 后端src单元测试：117个文件、881项通过；最终容量计算相关27项另行复核通过。
- 小程序相关测试：38项通过，包括变更文案后的错误码处理、刷新失败、冲突恢复、重复提交保护、卸载、会话切换与地图回归。
- PostgreSQL：历史/版本7项、旧库迁移3项、报表13项、场地设置3项、订场/培训并发30项，共56项通过。
- HTTP公开访问与设置权限10项通过。
- API构建/lint、小程序类型检查、微信生产包检查通过，包含实际编译后的地图分支检查。
- H5浏览器通过场地CRUD、旧表单冲突、重新加载、模拟写入成功后GET失败并恢复、人员/会员权限入口与小屏布局；无浏览器错误。截图见evidence。
- 新增 `availability_history`、`availability_migration` 两个核心验收分组，已接入现有CI流程并实际通过。迁移验收使用Prisma构建前一版本的数据库，再对带旧数据的数据库执行真实新迁移。

回归夹具同时补齐了历史创建时间、合法代订关联订单及状态约束，并消除了依赖“报表第一行”的脆弱断言。未以修改数据库约束的方式让测试通过。

## 发布与边界

先执行迁移、生成Prisma客户端，再切换后端；与包含业务错误码及结果合同的小程序配套发布。迁移在事务内回填并安装触发器，会锁定相关表以防迁移期间并发写入遗漏。

本轮没有额外的外部服务依赖。数据库和浏览器验收均为本地隔离环境，未修改生产数据；微信真机、实际支付及正式发布尚未执行。
