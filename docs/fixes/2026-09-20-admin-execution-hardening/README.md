# 管理员直接执行：事务、退款恢复与领域边界加固

日期：2026-09-20。状态：本地实现及验收完成，尚未部署或上传微信版本。

本记录补充并取代上一轮直接执行说明中的事务恢复、模拟服务和“无需数据库迁移”结论。管理员／超级管理员仍只需一次确认，可以处理自己的单据。

## 已修复的问题

| 问题 | 最终行为与验证 |
| --- | --- |
| 寄售结算先提交、确认，最后才发现付款凭证为空白 | 完整输入先校验；提交、确认、结算、状态记录及审计在一个 PostgreSQL 事务内完成。空白凭证不改变草稿；末步审计异常会回滚全部阶段。 |
| 培训结算由多个独立事务串联 | 同样在一个事务内组合原有状态命令；同账号权限、账本来源核对及并发检查继续生效。 |
| 活动取消后，退款执行依赖原请求继续运行 | 取消活动与登记 `ActivityRefundJob` 在同一事务内提交。后台分批处理，保存任务状态、重试时间、执行租约和错误摘要。新服务进程可接管过期租约并继续未执行部分。 |
| 旧数据库约束仍禁止管理员自行确认寄售单、发布青训规则 | 新迁移移除两条不支持角色例外的固定异人约束；由领域权限规则判断。普通财务仍不能确认自己的寄售／培训结算，青训发布仅限管理员。金额、状态、付款证据、唯一键和外键约束保留。 |
| 青训审计写死 ADMIN／SUPER_ADMIN 角色 | 审计写入实际操作人的角色。真实数据库测试验证两种管理员都能自行发布，失败后用原命令恢复草稿发布。 |
| 模拟服务总路由按 URL 串联多个业务领域 | 直接执行逻辑归还会员、培训、库存、活动等领域；总路由只分发。公共幂等键算法无业务依赖；同步模拟结算支持原子提交和回滚。 |
| 只替换内部命令的测试无法发现数据库约束冲突 | 增加真实业务命令和 PostgreSQL 集成测试，并加入核心验收矩阵，后续可重复运行。 |

## 退款任务约定

- 管理员取消球局／赛事时登记任务，非管理员活动负责人仍生成退款申请。
- 每轮最多领取 4 个任务，每个任务处理 8 笔；每 5 秒扫描，租约为 120 秒。领取及更新均校验租约归属，多个实例不能重复领取同一有效任务。
- 请求取消后返回“退款已提交，系统会自动处理”；页面无需等整场退款完成。
- 任务只提交该活动关联订单中标记为必须退款、仍为 `REQUESTED` 的记录；包括取消前已存在的部分退款申请。成功部分不重复处理，无关订单不受影响。
- 提交失败后按延迟重试；已进入微信派发阶段的退款仍由原有 `RefundDispatchService` 恢复。
- `COMPLETED` 表示应退申请已提交处理，不表示微信资金全部到账。实际到账以退款记录、支付渠道回调与查询结果为准。
- 升级前已取消且没有任务记录的活动不会被自动补授权。其待处理退款仍从现有退款列表处理。

## 架构边界

业务规则仍由各领域负责，公共角色策略只判断直接执行资格。结算命令负责事务边界，单个状态转换负责校验及记录；未引入通用工作流引擎。

活动领域只在取消事务内写退款意图，订单模块的后台服务负责执行；活动模块不依赖订单模块的运行时退款服务。模拟环境演示一个完成的退款处理批次，服务重启和并发恢复由真实数据库测试验收。

会员调账、消课冲正、盘点和青训发布仍保留可重试的申请／草稿记录。它们不等同于本轮已经原子化的两类结算；最终入账命令沿用原有事务与幂等保护。

数据库验收使用独立的本机 PostgreSQL。核心验收脚本会为分组创建临时数据库、运行全部迁移、执行测试并清理。微信外部支付使用测试替身，业务命令、状态更新、审计及账本操作使用真实数据库；没有访问生产数据或执行真实退款。

一次同时启动多项构建与全量测试时，两个既有登录生命周期测试的准备钩子超时。降低测试进程并发后，全量 525 项通过；没有放宽超时断言或跳过测试。历史 HTTP 路由套件中的 426 问题本轮未重试或绕过，不能据此声称所有 HTTP 路由均已验收。微信真机与实际到账仍需发布时确认。
