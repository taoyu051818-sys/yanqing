# 第十五轮修复：培训退费后的名额与名单同步

## 行为变化

- 培训报名建单与支付激活共用有效占位条件：在读/部分退款且仍有可用预收余额。消课后退清剩余费用的报名不再占位，原学员可重新购买，新学员也可报名付款；仍有可用余额的部分退款报名继续占位。
- 保留订单与报名的累计退款事实，例如已消课 10 元、退回剩余 90 元，仍记录部分退款；不把已确认收入抹掉来释放名额。
- 余额退款成功与微信退款成功通知共用 `applyTrainingRefund`，在同一事务内更新预收账本，并在余额归零时取消尚未到场、尚未消课的待处理考勤，解除待履约的补课关联，记录取消原因与原状态。
- 已有签到、消课、收入确认及缺勤记录保持原样；需要更正的历史仍走既有流程。重复审批/通知不会重复退钱或生成名单释放审计。
- 历史零余额部分退款报名也会被新占位查询排除。本轮没有批量回写历史遗留考勤。

## 验证

- 新增 `training-refund-roster.integration.spec.ts`，13 项 PostgreSQL 回归通过，覆盖余额与微信两条路径、退清剩余金额后原学员重购和新学员付款、全退后正常结课、有效余额占位、补课释放、签到/已消课证据保留、重复退款通知及审计失败时的整体回滚。
- API 常规测试 837 项通过，API 构建和 lint 通过；lint 仅有既有 `orders.journey-closeout.spec.ts` 未使用导入警告。
- 在另一全新隔离数据库运行既有支付生命周期、会员与培训权益套件，32 项通过；本轮数据库验证合计 45 项。
- CI 新增独立培训退费测试数据库，避免被其他套件的已关账日期和结算记录影响。

微信验证经过通知处理入口，但使用本地模拟的预支付/退款响应、签名校验和解密结果，未发起真实外部支付或退款。不需要数据库迁移。本轮仅完成本地修复、验证与 GitHub 同步，尚未部署生产。
