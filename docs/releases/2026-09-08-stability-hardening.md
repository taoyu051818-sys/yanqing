# 核心链路稳定性修复与架构整理

本轮落实架构抽查中确认的四个问题，并补充共享接口类型和持续集成。保留现有模块化单体结构，暂不拆分服务。

## 业务修复

1. 取消未支付订单时，重新检查事务内出现的微信支付请求；若与关单前读取的记录不一致，拒绝本次取消并提示刷新重试，防止直接释放场地。
2. 已取消订单收到迟到的成功付款回调时，记录实际收款、生成待财务核对的补偿退款及高优先级关键事件。补偿退款必须原路退回，不恢复场地或报名权益，也不扣减原有充值余额或重复返还库存；重复通知保持幂等。
3. 超时扫描在启动和每次定时执行时均覆盖全部待支付业务类型，不再仅持续扫描订场。
4. 小程序订场日期切换仅接纳最后一次请求的结果；过期请求的失败和完成事件也不会覆盖当前加载状态。
5. PC 老板摘要使用已加载指标的日期生成简报，并提示筛选日期尚未应用，避免指标与文字摘要日期不一致。

其中第 1、2 项共同修复取消与支付的竞态。财务补偿仍遵守现有审批权限和审核流程，不自动批准退款。

## 架构整理

- 格式化 PC 管理后台和老板摘要服务，使原先压缩在长行中的代码可读、可审查。
- 在 `packages/shared` 中定义老板摘要、经营指标、活动、关键事件与简报契约；API 返回值和 PC 消费端共同使用这些类型。
- 新增 PC 摘要日期回归测试，并纳入根目录验收命令。
- 新增 GitHub Actions：依赖锁定安装、类型和 lint 检查、单元测试、API e2e、隔离 PostgreSQL 集成测试及三个生产应用构建。

## 后续边界

本轮没有完成大型订单服务、经营台配置和 mock 路由的全面拆分，也没有引入 Outbox 或支付主动对账任务。微信网络调用仍有部分位于数据库事务内；这些应继续按业务域逐步整理，并使用现有回归测试保护行为。LLM 服务器连接问题不属于本次改动。
